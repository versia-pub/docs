The Versia Protocol is designed as a communication medium for federated applications, using the HTTP stack. Its simplicity ensures ease of implementation and comprehension.

## Audience and Scope

This specification is for people implementing a Versia server or library.

It covers what instances exchange with each other: [entities](/entities), [signatures](/signatures), [HTTP routes](/federation/endpoints) and [extensions](/extensions), plus [Versia Links](/links) for opening addresses. It does not cover client APIs, storage, account management or moderation policy.

## Vocabulary

The key words **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT** and **MAY** in this specification are to be interpreted as described in BCP 14 ([RFC 2119](https://datatracker.ietf.org/doc/html/rfc2119), [RFC 8174](https://datatracker.ietf.org/doc/html/rfc8174)) when, and only when, they appear in bold capitals, as shown here. In any other form, these words have their everyday meaning and set no requirement.

An Instance conforms to this specification if it meets every **MUST** and **MUST NOT** of the core protocol, and of each [extension](/extensions) it lists in [`compatibility.extensions`](/entities/instance-metadata). Extensions are optional.

## Philosophy

The Versia Protocol is heavily inspired by the [ActivityPub](https://www.w3.org/TR/activitypub/) specification. It is designed to be simple and easy to implement, with a focus on the following concepts:
- **Simple Structures**: Entities are represented as JSON objects. No JSON-LD, no complex data structures, just plain JSON.
    - As structures are kept simple, they are easy to parse with strongly-typed languages like Rust.
- **Modularity**: The protocol is divided into a **core protocol** and **extensions**. Implementations can choose to support only the core protocol or add extensions as needed.
- **Namespacing**: To avoid extension conflicts, all extensions are namespaced.
- **Signatures**: Requests and responses between instances **MUST** be signed with the instance's private key, apart from [a few routes](/signatures#where-signatures-are-required). Unlike other protocols, signatures are **mandatory**, not optional.
- **Developer-Friendliness**: Understanding and implementing your own Versia server should be easy. Documentation is aimed at developers first.
