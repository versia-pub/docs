Implementations **MUST** strictly validate all incoming data to ensure that it is well-formed and adheres to the Versia Protocol. If a request is invalid, the instance **MUST** reject it with the matching [status code](/federation/http#status-codes).

Remember that while *your* implementation may disallow or restrict some user input, other implementations may not. You **should not** apply those restrictions to data coming from other instances.

For example, if your implementation disallows using HTML in posts, you should not strip HTML from posts coming from other instances. You *may* choose to display them differently, but you should not modify the data itself. [Sanitizing HTML before rendering it](/security#remote-content) does not change this: it applies to what you display, not to what you store.

Things that should be validated include, but are not limited to:

- The presence of **all required fields**. [Optional fields](/json#optional-fields) may be omitted or `null`.
- The **format** of all fields (integers should not be strings, timestamps should be in RFC 3339 format, etc.). Whether a well-formed date is plausible is up to your implementation.
- The presence of **all required headers**.
- The presence of a **valid signature**, where [one is required](/signatures#where-signatures-are-required).
- The **author** of each entity, as described [below](#authors-and-signers).
- The **length** of all fields (for example, the `username` field on a `User` entity) should be at least 1 character long.
  - Do not set arbitrary limits on the length of fields that other instances may send you. For example, a `bio` field should not be limited to 160 characters, even if your own implementation has such a limit.
  - If you do set limits, they should be reasonable, well-documented and should allow Users to easily view the remote original, by, for example, linking to it. A limit of `100 000` characters for a `bio` field is acceptable, but a limit of `160` characters is not.
- The **type** and **range** of all numeric fields.
  - For example, a `size` field on a `ContentFormat` structure should be a non-negative integer, not a negative number or a fractional one.

  All numeric fields in these docs state their [type](/json#numbers) (`u64` or `f64`). As a rule of thumb, do not use a smaller type in memory than the one specified in the docs.

- The **validity** of all URLs and URIs (run them through your favorite URL parser).

It is your implementation's duty to reject data from other instances that does not adhere to the strict spec. **This is crucial to ensure the integrity of your instance and the network as a whole**. Allowing data that is technically valid but semantically incorrect can lead to the degradation of the entire Versia ecosystem.

## Authors and Signers

An entity's `author` **must** belong to the instance that signed the message carrying it, whether the entity was delivered to an inbox or fetched. This also applies to each entity in a [Collection](/structures/collection)'s `items`.

An instance **must** reject an entity that breaks this rule. If it checks before answering an inbox request, it **must** return a `422 Unprocessable Entity` status code. If it processes the entity after answering, it **must** drop the entity, and no status code is required.

Entities without an `author` field state which instance may send them on their own page.

## Unknown Fields and Types

Receivers **must** ignore fields they do not recognize on entities and structures, and **must not** reject an entity for having them. They do not need to store them. This is what lets a `0.X.Y` release add optional fields.

An entity whose `type` the receiver does not recognize is handled by what kind of type it is:

- A namespaced type, which belongs to an [extension](/extensions#naming), **must** be answered with a `2xx` status code and dropped.
- Any other type is a core type, and **must** be rejected with a `422 Unprocessable Entity` status code. Core types only change between `X` versions, so an unknown one is an invalid entity.
