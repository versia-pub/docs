Versia provides a set of core entities and structures to build a barebones social network. However, it is not possible nor desirable to cover every use case. This is where extensions come in, allowing parts of the system to be extended or replaced with custom functionality.

By design, extensions can be implemented in any combination, without requiring any changes to the core system. This allows for a high degree of customization and flexibility. Implementations that do not support a particular extension can simply ignore it without any issues.

Extensions **SHOULD** be standardized and publicly documented.

## Documented Extensions

These extensions are documented on this site, and all use the `pub.versia` namespace and are at [version](#versions) 1. See [Naming](#naming) for how their names are formed.

An extension does not need to be listed here to be used. To propose one for this list, [open an issue](https://github.com/versia-pub/docs/issues).

## Handling Unsupported Extensions

When an extension is not supported by an Implementation, it can be ignored. This means that the extension is not processed, and its data is not used. Implementations **MUST NOT** throw an error when encountering an unsupported extension, as long as the rest of the entity is valid. An entity whose type comes from an unsupported extension is [answered with a `2xx` status code and dropped](/validation#unknown-fields-and-types).

Extensions **MUST NOT** be designed in a way that makes them required to understand or process other non-extension entities.

## Naming

Versia extension names are composed of two parts:
- The domain name of the extension author, in reverse order. Example: `pub.versia`
- The extension name, separated by a colon, in `snake_case`. Example: `likes`

```text title="Example Extension Name"
pub.versia:likes
```

The namespace **MUST** come from a domain the author controls. `pub.versia` is reserved for extensions defined in this specification.

### Custom Entities

Custom entities are named in the same way, but with an additional part:
- The entity name, separated by a slash, in `PascalCase`. Example: `Like`

```text title="Example Custom Entity Type"
pub.versia:likes/Like
```

## Versions

An extension's version is a whole number that starts at 1, and goes up only when a change is incompatible. Extension keys, entity types and endpoints do not include it.

Instances list what they support in [`compatibility.extensions`](/entities/instance-metadata), as the extension name and version joined by `@`. They **MAY** list several versions of an extension.

```text title="Example Supported Extension"
pub.versia:likes@1
```

Two instances that both list an extension use the highest version they have in common. If they have none in common, the sender **MUST** leave out that extension's data: its key in `extensions`, its entity types and its collections.

## Extension Definition

Extensions can add any of the following:

- Custom functionality on an existing entity, through its [`extensions` property](#entity-extension).
- New entity types, as [custom entities](#custom-entity).
- [Collections](#collections) on an entity.
- [Endpoints](#endpoints).
- [Interaction types](/extensions/interaction-controls).

### Entity Extension

<Fields name="EntityExtension">
    <Field name="extensions" type="Record<string, JSONData>">
        Custom extensions to the entity.

        - `key`: The extension name.
        - `value`: Extension data. **MUST** be a JSON object, following [Versia JSON rules](/json).
    </Field>

    <Example slot="example" unchecked>
    ```jsonc title="Example Entity Extension"
    {
        "type": "pub.versia:groups/Group",
        "id": "ed480922-b095-4f09-9da5-c995be8f5960",
        "created_at": "2021-01-01T00:00:00Z",
        "open": true,
        "extensions": { // [!code focus:100]
            "com.example:gps": {
                "location": {
                    "latitude": 37.7749,
                    "longitude": -122.4194
                },
                "accuracy": 10,
                "name": "San Francisco"
            }
        }
    }
    ```
    </Example>
</Fields>

### Custom Entity

<Fields name="CustomEntity">
    <Field name="type" type="string" required>
        The extension type, [following naming conventions](#naming).
    </Field>
    <Field name="other">
        Other properties of the custom entity. These are specific to the extension, and should be documented by the extension author.

        Note that `id` and `created_at` are still required for custom entities, unless the extension author specifies otherwise.
    </Field>

    <Example slot="example" unchecked>
    ```jsonc title="Example Custom Entity"
    {
        "type": "com.example:poll/Poll",
        "id": "6f27bc77-58ee-4c9b-b804-8cc1c1182fa9",
        "author": "example.com:6e0204a2-746c-4972-8602-c4f37fc63bbe",
        "created_at": "2021-01-01T00:00:00.000Z",
        "question": "What is your favourite colour?",
        "options": [
            "Red",
            "Blue",
            "Green"
        ]
    }
    ```
    </Example>
</Fields>

### Collections

An extension's [collections](/structures/collection) are named like its custom entities, for example `pub.versia:likes/Likes`.

### Endpoints

An extension's endpoints **MUST** be under `/.versia/v0.X/extensions/<extension name>/`. This keeps them from colliding with core endpoints or with other extensions. The extension name is [not percent-encoded](/federation/http#encoding).

```text title="Example Extension Endpoint"
/.versia/v0.7/extensions/pub.versia:instance_messaging/messaging
```
